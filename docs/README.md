# OctoAcme Project Management Documentation

## Overview
OctoAcme follows a structured, iterative approach to project management that emphasizes customer value, clear ownership, measurable outcomes, and continuous learning. The project lifecycle starts with initiation and validation, moves into planning and backlog definition, continues through execution and tracking, and closes with release verification and retrospectives. This documentation suite provides a consistent framework for managing work from idea to delivery while making roles, responsibilities, and decision points explicit.

The OctoAcme approach is grounded in a few core principles: customer-first delivery, iterative progress, transparent ownership, data-informed decision making, and psychological safety. These principles help teams align on what matters, reduce friction across functions, and maintain momentum while managing ambiguity. This documentation acts as a practical knowledge base for teams and stakeholders navigating the full project lifecycle.

## Core Process Areas
OctoAcme’s project management model covers the key phases of work:
- Initiation: Validate the business need, align stakeholders, define success metrics, and decide whether to proceed.
- Planning: Convert ideas into actionable backlog items, milestones, dependencies, and release plans.
- Execution & Tracking: Run daily/weekly delivery rhythms, monitor blockers, maintain quality standards, and report status.
- Risk & Communication: Manage issues, dependencies, and escalation paths while keeping stakeholders informed.
- Release & Deployment: Prepare for production readiness, validate deployment quality, and manage rollback plans.
- Retrospective & Improvement: Capture lessons learned, document action items, and improve future delivery.

## How to Use This Knowledge Base
1. Start with the [Project Management Overview](octoacme-project-management-overview.md) to understand the OctoAcme model and core roles.
2. Use the phase-specific documents in sequence as work moves from initiation to close-out.
3. Reference cross-phase topics such as risks, communication, and retrospectives when issues or decision points arise during delivery.
4. Keep the project one-pager, risk register, release notes, and key decisions updated in the project repo.
5. If you want Copilot Spaces to use project-specific context, add a relevant process doc to the `.copilot/` folder.

## Guidance for Team Members
This documentation is meant to reduce onboarding friction and provide a single entry point for project knowledge. Use it as a practical playbook for planning, reporting, quality, communication, and learning. For most project work, the best path is to begin with the project overview, move through the project lifecycle documents, and then use the supporting guides as needed for risk management, stakeholders, and continuous improvement.
